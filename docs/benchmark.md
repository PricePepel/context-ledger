# M0 benchmark: graph context vs Markdown handoff

Generated by `bench/m0.mjs` on 2026-11-07 at commit `7dcb7468bf78`, seed 42. All transcripts are synthetic. Everything except timings, date, commit and machine is deterministic for a seed.

Reproduce:

```sh
node bench/m0.mjs --seed 42 --sizes 10,50,200,1000 --reps 20 --append 10 --markdown docs/benchmark.md
```

Machine: Node v22.23.4, linux x64, 4 x Intel(R) Xeon(R) Processor @ 2.30GHz.

Each size is the number of conversation turns per party. Party `mara` is a Claude Code JSONL transcript and party `teo` a Codex rollout; `teo` links to `mara` with matches, conflicts and answers, and the two graphs open one room.

## 3. Cache-prefix stability

Method: 10 turns are appended to the transcript and it is imported again. The store keys a session by the hash of its transcript, so the longer transcript becomes a new session. A revised graph with the same nodes plus one new action is published against it. The table shows the longest common leading byte prefix of the old and new output as a share of the new output. A prefix counts as cache-eligible only from 1024 estimated tokens, the safe minimum across Anthropic's older models and OpenAI (the newest Claude models accept 512).

| Turns | Party | Graph prefix share | Graph prefix tokens (est.) | Graph cache-eligible | Handoff prefix share | Handoff prefix tokens (est.) | Revised graph recall |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 10 | mara (claude) | 50.9% | 149 | no | 2.8% | 21 | 1 |
| 10 | teo (codex) | 41.7% | 145 | no | 2.7% | 21 | 1 |
| 50 | mara (claude) | 49.4% | 193 | no | 1.0% | 21 | 1 |
| 50 | teo (codex) | 44.4% | 205 | no | 1.0% | 21 | 1 |
| 200 | mara (claude) | 52.5% | 290 | no | 0.3% | 21 | 1 |
| 200 | teo (codex) | 43.6% | 292 | no | 0.3% | 21 | 1 |
| 1000 | mara (claude) | 54.3% | 537 | no | 0.1% | 21 | 1 |
| 1000 | teo (codex) | 47.0% | 553 | no | 0.1% | 21 | 1 |

The Markdown handoff prints the session ID in its fifth line, and the session ID changes with every append, so its common prefix ends there. The graph context keeps the session and graph IDs in its last section, but its prefix ends earlier than the action section: the new action also adds an `advances` edge, and the edges section comes before links and actions, so the change lands in the middle of the output. Here the stable prefix stays below the cache minimum at every size.

## Method and limits

- Inputs are synthetic negotiations from a seeded PRNG (mulberry32). Most turns are filler work chatter; planted facts (about sqrt(turns) + 4 per party) sit at known lines. Real sessions have longer turns, tool output and code, so absolute sizes and ratios will differ.
- The benchmark writes the graph packets itself. It measures storage, canonicalisation and rendering through the real HTTP API, not how well an agent extracts a graph from a transcript.
- Token figures are estimated as characters / 4 and are not tokenizer counts. Real counts vary by model (Claude 4.7 and later tokenizers emit about 30% more tokens for the same text) and by content: structured text, digits and code usually yield more tokens per character than prose, so the token saving may differ from the character saving. Section 6 shows the content mix of each side.
- The graph context is compared with the full Markdown handoff of the same transcript, which is the baseline the API meter uses. A hand-written summary would be a different, smaller baseline.
- Cache savings need a prefix above the provider minimum and a follow-up request within the cache lifetime. Changing tools, the system prompt or thinking settings invalidates a cache whatever Context Ledger outputs.
- The server runs as a child process on a free loopback port with a fresh temporary database, which is deleted at the end. Latency includes local HTTP and JSON overhead and is a single-machine measurement.
